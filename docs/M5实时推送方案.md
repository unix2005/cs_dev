# M5 实时推送（轨迹 + 报警）详细方案

> 状态：待评审（评审通过后开始写代码）  
> 范围：客户端实时推送长连接 + 后端推送微服务 `q_s_vmsv1__push` + 配置/协议契约  
> 关联里程碑：M1 登录闭环、M4 会话治理（keeper）、M7 配置层（qc_conf / vms_client_conf，已落地）

---

## 0. 已裁定决策（本次确认）

| # | 决策点                      | 结论                                                                     |
| - | ------------------------ | ---------------------------------------------------------------------- |
| 1 | 推送端口是否走 knockd 隐藏        | **是**；但与命令端口是**两套独立服务实例**（各自 knockd+netd+后端），不是单进程开双端口。各实例端口从 XML 配置读取 |
| 2 | 订阅方式                     | **增量**（ADD / REMOVE 车辆 ID 的 delta），非全量重发                               |
| 3 | 报警与轨迹回调                  | **两个独立回调**（`vms_push_cb` 轨迹 / `vms_alarm_cb` 报警）                       |
| 4 | 后端推送服务 `q_s_vmsv1__push` | **由本会话实现**（无真实数据，自造少量测试数据）                                             |
| 5 | 推送节奏                     | **无 2~5s 节奏**，完全事件驱动：有数据立即推，没数据不推                                      |
| 6 | 推送连接建立时机                 | 客户端**登录成功后建立**；用户不选车 → 无轨迹推送（报警仍按组织子树推）                                |
| 7 | 推送服务器地址                  | 写进 XML 配置，**支持域名**形式，便于更换服务器                                           |

## 1. 目标与范围

### 1.1 目标

- 客户端在车辆树上勾选要监控的车辆 → 通过**独立推送长连接**把订阅（增量）发给后端。
- 后端推送服务从（模拟）轨迹队列读出数据，按"订阅车辆集合"过滤轨迹、按"用户组织子树"过滤报警，**实时**推回客户端。
- 推送走**独立长连接**，与命令通道（biz 查询 / 心跳 / 重连）互不干扰。
- 推送端口同样受 knockd 隐藏 + SM2/SM4-GCM 保护，不降低安全基线。

### 1.2 范围内

- `vms_core`（native）：第二条推送连接、接收/分发线程、两个回调、增量订阅发送、无后端 mock 退化、独立重连。
- C# 客户端：车辆树勾选 → 发送订阅 delta；新增 `AlarmPushed` 事件与 UI 接收。
- 后端 `q_s_vmsv1__push`：进程骨架、netd UDS 接入、模拟队列 + 少量测试数据、过滤与实时推送。
- `netd` / `knockd`：**无需改双端口代码**。改为"配置驱动启动两套实例"——命令实例（`listen_port=18099` / `ipc_path→bizd.sock` / SPA UDP `5001`）、推送实例（`listen_port=18098` / `ipc_path→pushd.sock` / SPA UDP `5002`），各自从独立 XML 读取端口与后端 UDS。
- 配置层：客户端 XML 新增 `push` 段（`host`/`port`/`knock` 域名或 IP）；连接层支持域名解析。
- 协议契约：netd↔pushd UDS TLV、推送连接上的 cmd 字与帧格式。

### 1.3 范围外

- 真实消息队列（Kafka / Redis Stream）接入 —— 本期用进程内模拟队列替代。
- 真实轨迹/报警数据源 —— 自造测试数据（6 辆车 + 2~3 条报警，足够验证链路）。
- 推送服务的水平扩容 / 多实例 —— 不在本期。

## 2. 总体架构

```
                ┌──────────────── 客户端 ────────────────┐
                │  车辆树勾选 → 订阅delta                  │
                │  接收线程(阻塞收包·持推送连接)           │
                │  vms_push_cb(轨迹) / vms_alarm_cb(报警)  │
                │        ↑ SUBSCRIBE delta │ TRAJ/ALARM ↓  │
                └───────┬───────────────────────┬─────────┘
         命令通道(现有) │                        │ 推送通道(新增,独立长连接)
               ↓       │                        │       ↓
   ┌──────── 命令栈(实例1) ────────┐   ┌────── 推送栈(实例2) ────────┐
   │ knockd_A(UDP 5001) 隐藏端口    │   │ knockd_B(UDP 5002) 隐藏端口 │
   │ netd_A(TCP 18099)+SM2/SM4-GCM  │   │ netd_B(TCP 18098)+SM2/SM4-GCM│
   │   └─UDS─> q_s_vmsv1__biz(现有)│   │   └─UDS─> q_s_vmsv1__push(新)│
   └───────────────────────────────┘   └─ push服务:读队列·按订阅/组织过滤·实时推 ─┘
   注：两栈各自独立进程、独立 XML 配置；netd 对后端类型无感知，只按 ipc_path 转发
```

- **推送连接与命令连接是两条独立的 TCP**：各自独立握手、独立 seq 空间、独立重连。
- **推送栈的 netd_B 同样终结 SM2/SM4-GCM**，再经 Unix Socket 转发给 `q_s_vmsv1__push`（与 bizd 完全平行的安全模型：公网只面对非 root / chroot / seccomp 的 netd，后端微服务不直接暴露）。
- **netd / knockd 无需改双端口代码**：它们本就是 XML 配置驱动（`-c` 指定配置文件），且 netd 只按 `ipc_path` 把流量转给后端、由后端自己 demux；knockd 开门的 TCP 端口是从 SPA 报文的 `req_port` 解出来的（客户端在 SPA 里携带目标 TCP 端口）。因此"双端口"只需**起两个实例、各读一份 XML**，不碰 netd/knockd 源码。
- **域名支持**：`push.host` 可为域名；连接层改用 `getaddrinfo` 解析（现状 `q_net` 只认 `inet_pton` 字面 IP，必须改造）。

## 3. 部署 / 网络拓扑与 knockd

### 3.1 端口与敲门（两套独立实例）

- **命令栈实例**：`knockd_A` 监听 UDP `5001`，开门目标 TCP `18099`；`netd_A` 监听 TCP `18099`，`ipc_path` 指向 `bizd.sock`。
- **推送栈实例**：`knockd_B` 监听 UDP `5002`，开门目标 TCP `18098`；`netd_B` 监听 TCP `18098`，`ipc_path` 指向 `pushd.sock`（push 服务的 UDS）。
- 开门的 TCP 端口**不是 knockd 配置的**，而是客户端 SPA 报文里携带的 `req_port`：`qc_knock(knock_udp_endpoint, target_tcp_port)` —— 命令连接敲 `5001` 带 `18099`，推送连接敲 `5002` 带 `18098`。knockd 收到合法 SPA 后用 `req_port` 往 nft 集合加 TTL 元素。
- 两栈**共用同一把 SPA 共享密钥**（配置里 `knock.spa_key_path` 不变）；建议也**共用同一套服务端 SM2 身份密钥**（两个 netd 实例用同一 keypair，客户端只内置一份公钥即可，详见 8.2）。

### 3.2 独立部署（同机两份配置 / 异机各一份）

- `push.host` / `push.port` / `push.knock` 与 `server.*` **彼此独立**，允许推送栈部署在另一台机器 / 另一域名下。
- 异机部署时，那台机器自带 `knockd_B` + `netd_B` + `q_s_vmsv1__push`，并用自己的 `knockd_conf.xml` / `netd_conf.xml` 指定 UDP `5002` / TCP `18098` / `pushd.sock`。客户端只认配置里的 `push.host:push.knock:push.port`。

### 3.3 连接时序（客户端）

1. 启动：敲两套门——`knock(knockd_A_UDP=5001, target=18099)` + `knock(knockd_B_UDP=5002, target=18098)`（均为预认证，可顺序/并行；对应配置 `server.knock` 与 `push.knock`）。
2. 建命令连接 → SM2 握手 → SM4-GCM 协商 → 登录（沿用 M1/M4 链路）。
3. 登录成功后：**建推送连接** → SM2 握手 → SM4-GCM 协商 → 发 `PUSH_SESSION_BEGIN`（org 由 token 在服务端推导，客户端不传 org）→ 发初始 `SUBSCRIBE_DELTA`（空集合）。
4. 用户在车辆树勾选/取消 → 仅发送 **delta**（ADD / REMOVE 变动的车辆 ID）。
5. 收到 `PUSH_TRAJ` → `vms_push_cb`；收到 `PUSH_ALARM` → `vms_alarm_cb`。

### 3.4 重连

- 命令连接由 M4 keeper 重建（已含重新敲 `knockd_A`）。推送连接**独立**重建：掉线 → 重新 `knock(knockd_B_UDP=5002, target=18098)` → 重连 → 重握手 → 重发 `PUSH_SESSION_BEGIN` + **重放当前完整订阅集合**（服务端会话已丢，必须全量重放，但这次全量只发生在重连时，平时仍是增量）。

## 4. 配置文件变更（XML）

### 4.1 新增 `push` 段（点分键，由 q_xcfg 读取，零结构体改动）

```
vms_client.push.host   = push.example.com   ; 域名或 IPv4/IPv6 均可
vms_client.push.port   = 18098              ; netd_B 的 TCP 监听端口
vms_client.push.knock  = push.example.com:5002  ; knockd_B 的 UDP SPA 端点
```

- 复用现有点分键机制（`QC_K_*` 常量 + `q_xcfg`），只读不改内存布局。
- `push.knock` 是**推送栈 knockd 的 UDP 端点**（与命令栈 `knock.endpoint` 不同端口）；敲门时客户端把 `push.port` 作为 `req_port` 带进 SPA，knockd_B 据此开 `18098`。

### 4.2 native `vms_client_conf` 结构体（ABI v8，定长）

在现有 `vms_client_conf` 末尾追加：

```c
char    push_host[256];   /* 域名或 IP；为空则回退用 server.host */
uint32_t push_port;       /* 0 则回退用 server.port */
char    push_knock[256];  /* 推送栈 knockd UDP 端点 host:port；为空回退 server.knock */
```

- 追加字段改变 `sizeof` → **ABI 升 v7 → v8**，C# `ExpectedAbiVersion` 同步；C# 侧结构体追加对应字段。
- 回退语义：未配 `push` 段时，推送连接复用命令连接的 `host/port/knock`（兼容单端口部署）。

### 4.3 域名解析改造（必须项）

- 现状：`lib_src/l_2/q_net/api/q_net_connect.c` 与 `q_net_connect6.c` 只用 `inet_pton`（纯 IP）。
- 改造：新增域名感知的连接入口（或改造 `q_net_addr_resolve.c` 先 `getaddrinfo` 解析，再 `connect`），命令连接与推送连接**统一走解析层**，从此全栈支持域名。
- 解析可能阻塞 → 必须在后台线程（推送连接建立本就在原生线程上下文，天然不阻塞 UI）。

## 5. 线缆协议（Wire Contract）—— 核心

### 5.1 客户端 ↔ netd（公网，复用现有私有二进制帧）

- **完全复用**现有帧格式：44B 包头（整体作 AAD）+ SM4-GCM 密文 + 16B tag；IV = `nonce_base XOR seq`（禁止随机 IV）；seq 滑动窗口 `[last+1, last+64]`、时间戳 ±300s 粗筛；Token 绑定 `channel_id/user_id/device_id/src_ip`。
- 推送连接是**第二条独立连接**，拥有自己的 seq 空间（与命令连接互不干扰，避免重放窗口交叉）。
- 新增 cmd 字（在现有命令字体系内扩一档，例如 `0x02xx` 推送域）：

| cmd 字（草案）        | 方向  | 含义                  | 负载（内层 TLV）                                                                          |
| ---------------- | --- | ------------------- | ----------------------------------------------------------------------------------- |
| `PUSH_BEGIN`     | C→S | 标记本连接为推送会话          | 无（org 由 token 推导）                                                                   |
| `PUSH_SUB_DELTA` | C→S | 增量订阅（可连续多帧分片，见 7.6） | `op`(ADD/REMOVE) + `vehicle_id[]`（每帧 ≤ 约 500 个 ID，避免单帧超 `Q_IPC_TLV_MAX`）            |
| `PUSH_TRAJ`      | S→C | 轨迹点                 | `vehicle_id`, `lon`, `lat`, `speed`, `time`, address, is_alarm, …                   |
| `PUSH_ALARM`     | S→C | 报警事件                | `vehicle_id`, `org_id`, lon, lat,`alarm_type`, `time`, `text`,`alarm_address`,`...` |

### 5.2 netd ↔ q_s_vmsv1\_\_push（Unix Socket，新增契约，写入 `include/include_ipc_proto.h`）

- 复用现有 `Q_IPC_T_*` 外层 TLV 框架（`Q_IPC_T_CMD` / `Q_IPC_T_BODY` / `Q_IPC_T_CHANID` / `Q_IPC_T_USERID` / `Q_IPC_T_TOKEN` 等）。
- 新增推送专用内层 tag（草案，避免与 biz 冲突）：
  - `Q_IPC_T_PUSH_OP`   —— SUB_DELTA 的操作（ADD/REMOVE）
  - `Q_IPC_T_PUSH_VIDS` —— vehicle_id 列表（多个 `Q_IPC_T_PUSH_VID` 元素）
  - `Q_IPC_T_PUSH_TRAJ` —— 轨迹点负载
  - `Q_IPC_T_PUSH_ALARM`—— 报警负载
- netd 在推送连接上收到 `PUSH_BEGIN` 后，从已验证 token 提取 `user_id` + `org_id`，向 push 服务发 `PUSH_SESSION_BEGIN{chan_id, user_id, org_id}`；之后 `PUSH_SUB_DELTA` 透传为 `PUSH_SUBSCRIBE{chan_id, op, vids}`。
- push 服务产生 `PUSH_TRAJ` / `PUSH_ALARM` 时，带 `chan_id` 回 netd，netd 在对应推送 TCP 上加密下发。

### 5.3 实时性约束

- **服务端无定时器节奏**：push 服务内部"数据生成器"产生数据点即过滤即推，没有"每 N 秒扫一遍"的逻辑。
- 客户端无数据时**不收任何帧**（接收线程阻塞在 `recv`），自然零空转。

## 6. 客户端（vms_core / C#）改造

### 6.1 native（vms_core.c / q_clientcomm）

- **第二条长连接 `push_conn`**：独立 socket、独立 owner 原生线程 `push_recv_thread`。
  - 走与命令连接相同的 `qc_knock` + SM2 握手 + SM4-GCM 协商流程（抽成可复用函数，避免重复）。
  - **不共享命令通道的 gate**（`qc_keeper_lock` 只锁命令通道）；推送连接的加解密用自身会话上下文，避免与心跳/重连互锁。
- **连接时序**：登录成功回调里触发"建推送连接"（见 3.3）。
- **增量订阅发送**：暴露 `vms_push_subscribe_delta(op, vids[], n)`；C# 在树勾选变化时调用，只传变动集合。
- **接收线程 demux**：解密帧 → 按 cmd 字分流：
  - `PUSH_TRAJ` → 现有 `vms_push_cb(items, count, user_data)`
  - `PUSH_ALARM` → **新增** `vms_alarm_cb`（新增注册 API `vms_set_alarm_callback`）
- **无后端降级**：连不上真实推送服务（或配置无 push 段）时，线程在本地生成 mock 轨迹（保留现有 `push_thread_proc` 的随机游走逻辑），UI 仍可动；报警 mock 可选。
- **独立重连**：推送连接掉线 → 独立重建（重新敲门 + 重握手 + 重放完整订阅集合）。与 M4 keeper 状态机咬合：keeper 进入 `ONLINE` 后若推送连接未建/已断，触发推送重建。

### 6.2 C# 侧

- 车辆树勾选/取消 → 调用 `SubscribeDelta(Add/Remove, ids)`（增量）。
- 新增 `event EventHandler<IReadOnlyList<AlarmRow>>? AlarmsPushed`；`OnNativeAlarm` 拷贝 → `Post` → `DispatcherQueue.TryEnqueue` → `AlarmsPushed`（**复用现有 UI 编组套路**，不碰 XAML 于原生线程）。
- `RealtimeMonitorViewModel` / 实时页消费 `AlarmsPushed`（报警面板/Toast）。

### 6.3 ABI 版本

- `VMS_ABI_VERSION` 升 **v8**：
  - `vms_client_conf` 新增 `push_host` / `push_port`（sizeof 变化）。
  - 新增 `vms_set_alarm_callback` 注册 API + `vms_alarm` 结构体（若有承载需求）。
  - `vms_struct_size` 增补新结构体；C# `ExpectedAbiVersion = 8`，`NativeModels` / `VmsCoreClient` 同步校验。

## 7. 后端推送服务 `q_s_vmsv1__push`

### 7.1 进程定位

- 后台微服务，**与 `q_s_vmsv1__biz` 平行**：经 netd 的 UDS 接入，不直接暴露公网。
- 进程骨架参照现有 biz 桩（`soft_src/q_s_vmsv1__biz`）：监听 UDS、按 `chan_id` 维护会话、读写 TLV。

### 7.2 会话管理

- 每推送连接一个会话：`{chan_id, user_id, org_id, 订阅集合(set<vehicle_id>)}`。
- 收到 `PUSH_SESSION_BEGIN` 建立会话；收到 `PUSH_SUBSCRIBE` 增量维护订阅集合（ADD 插入、REMOVE 删除）。
- 重连时会话重建，客户端重放完整订阅（见 3.4）。

### 7.3 模拟队列 + 测试数据（少量）

- **无外部 MQ**：进程内用"生成器线程 + 内存队列"模拟轨迹队列。
- 测试数据规模（够验证即可，不做大）：
  - **6 辆测试车**（固定 `vehicle_id`，如 `TEST-A0001`…`TEST-A0006`），随机游走生成 `lon/lat/speed/time`。
  - **2~3 条测试报警**，绑定到某个测试组织子树（如 `ORG_TEST` 及其下属）。
- 组织树：push 服务内置一棵**极简测试组织树**（根 + 2 层子节点），实现 `org_in_subtree(user_org, alarm_org)` 过滤（前端 M3 的 `company_in_subtree` 思路在后端重做一份，因后端是独立进程、不共享前端 mock）。

### 7.4 实时推送逻辑（事件驱动）

- 生成器线程：以**随机短间隔**（如 200ms~~2s 抖动，非固定 2~~5s）为每辆测试车产出轨迹点；以较低概率产出报警事件。
- 产出即过滤：
  - 轨迹点：仅推给"订阅集合包含该 `vehicle_id`"的会话。
  - 报警：仅推给"`user_org` 子树包含 `alarm_org`"的会话。
- 过滤命中即经 UDS 带 `chan_id` 发 netd → 下发客户端。**无任何周期扫描 / 固定节奏**。


### 7.5 与测试登录的衔接

- 测试登录账号的 `org_id` 应落在 push 服务的测试组织子树内，才能看到报警；订阅的 `vehicle_id` 命中 6 辆测试车之一，才能看到轨迹。该约定写进测试说明。

### 7.6 订阅集合规模：**不分页，支持任意大小**

- **裁定**：推送路径**完全不分页**。M3 的"单页上限 100 条"来自 `qc_biz_query` 一次性拉回"某单位全部车辆列表"时撞 `Q_IPC_TLV_MAX=60000`（单条 UDS/TLS 帧上限，一条车辆 JSON ≈ 480B，约 125 条封顶）。**该约束只作用于"拉列表"场景，与实时推送无关**：
  - 轨迹是**按车辆逐条事件驱动**下发的（每辆车一个轨迹点 = 一帧，几十字节），本来就不存在"一页 N 条"的概念；
  - 报警是**按事件逐条**下发的（一辆车的某次报警 = 一帧），同样无分页；
  - 一个单位下车辆数多或少、订阅多少辆，**都不该被 100 截断**。
- **随之而来的单帧上限约束（必须处理）**：客户端→服务端发 `PUSH_SUB_DELTA`（含 `vehicle_id[]`）以及服务端经 netd→客户端下发的单条帧，仍受 `Q_IPC_TLV_MAX=60000` 约束。若某单位 5000 辆车被一次性全订阅，单条 SUBSCRIBE 帧（5000×~40B ≈ 200KB）会超限被截断。
  - **应对：大集合用"分片 delta"，不是"分页查询"**。客户端把一次较大的 ADD/REMOVE 拆成多帧 `PUSH_SUB_DELTA`（每帧 ≤ 比如 500 个 ID，留足余量），服务端逐帧合并进订阅集合。重连时的"全量重放"同理分片发送。
  - 分片是**同一语义的增量续传**（没有 page 序号、没有"请求第 N 页"的语义），与"分页查询"有本质区别，符合"不分页"的裁定。
- **报警按组织子树**：若某组织子树含大量车辆，可能短时间内产生多条报警——每条独立成帧下发，不做聚合分页；若极端情况下需要合并，同样走"分片"而非"分页"。

## 8. netd / knockd 改动（核心结论：**无需改源码**）

> 经核查：`netd` 与 `knockd` 当前**已是 XML 配置驱动**（`-c /path/to/conf.xml` 指定配置），且两者都对"后端类型"无感知——
>
> - `netd` 只按配置里的 `ipc_path` 把整条连接的流量转给后端 UDS，由后端自己 demux 业务命令（bizd 如此，push 服务同理）；
> - `knockd` 开门的 TCP 端口**不是配置的**，而是客户端 SPA 报文里携带的 `req_port`（`q_spa_build` 写入、`q_spa_verify` 解出），knockd 用它在 nft 集合加 TTL 元素。
>
> 因此"双端口"**不需要在 netd/knockd 里写任何多端口逻辑**，只需**起两套实例、各读一份 XML**。

### 8.1 netd（零改动，仅两套配置）

- 命令实例 `netd_A`：`netd_conf.xml` 里 `listen_port=18099`、`ipc_path=/var/run/gtkvms/bizd.sock`、`sm2_priv/pub_file` 指向命令栈密钥。
- 推送实例 `netd_B`：另一份 `netd_push_conf.xml` 里 `listen_port=18098`、`ipc_path=/var/run/gtkvms/pushd.sock`、`sm2_*` 指向推送栈密钥（建议与命令栈**同一套**服务端身份密钥，见 8.3）。
- 两个 netd 二进制**完全相同**，差异只在配置文件。hardening（非 root / chroot / seccomp / 限流 / 字段校验）天然两套都生效。

### 8.2 knockd（零改动，仅两套配置）

- 命令实例 `knockd_A`：`knockd_conf.xml` 里 `listen_port=5001`（UDP）。
- 推送实例 `knockd_B`：另一份 `knockd_push_conf.xml` 里 `listen_port=5002`（UDP）。
- 开门的 TCP 端口由客户端 SPA 的 `req_port` 决定：命令连接敲 `5001` 带 `18099`，推送连接敲 `5002` 带 `18098`。两实例共用同一把 `spa_key`。

### 8.3 服务端 SM2 身份密钥（已裁定：共用一套）

- **裁定**：两个 netd 实例**共用同一套服务端 SM2 密钥对**（同一 keypair、`key_id` 同为 1）。客户端只内置**一份**服务器公钥（`auth.pubkey_path` 同时用于命令连接与推送连接），推送连接不再额外需要 `push_pubkey_path`，ABI 也不因此扩容。
- 理由：该密钥表达的是"服务器身份"而非"每端口身份"，命令栈与推送栈同属一个服务端，共用合理且维护成本最低。
- 若未来两栈真要异构部署到不同信任域，再升级为方案 B（各用独立密钥、客户端内置两份公钥）即可，不影响本次设计。

## 11. 风险与注意事项

1. **两条连接 seq 空间必须独立**：否则重放窗口交叉导致合法帧被吞或重放攻击面扩大。
2. **netd 限流是否误伤推送**：推送连接高频，netd 每源 IP 5/s 限流需确认对推送端口放宽或单独计（两个 netd 实例各自独立限流，可按推送实例单独调参）。
3. **域名解析阻塞**：必须放在原生后台线程，绝不能阻塞 UI 或命令连接建立。
4. **ABI v8 兼容性**：所有三端（native / C# / 测试 UT）必须同步抬版本，否则静默错位（M4 已踩过 v5 的坑）。
5. **组织子树判定在后端的正确性**：push 服务内置测试组织树，需与测试登录 `org_id` 对齐，否则报警看不到。
6. **推送连接与命令连接重连的解耦**：M4 keeper 只管命令连接；推送连接重建逻辑要独立且能感知 keeper 的 ONLINE 状态，避免"命令已连但推送没连"的半开状态。
7. **两套实例的运维代价**：两个 netd + 两个 knockd = 四个守护进程（外加 bizd + push 服务），各自需要 setcap（netd/knockd 需 CAP_NET_ADMIN）、各自 chroot/降权、各自日志。建议用 systemd 单元或容器分别管理，避免端口/集合冲突（nft 集合名在两 knockd 配置里可共用 `allow4/allow6`，也可分开）。
